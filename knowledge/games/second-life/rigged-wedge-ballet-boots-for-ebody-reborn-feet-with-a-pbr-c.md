# Rigged wedge ballet boots for eBody Reborn feet with a PBR color HUD (PRIM_GLTF_BASE_COLOR)

> A pair of rigged-mesh wedge ankle ballet boots for eBody Reborn's ballet foot (RebornFeet_5). They have
> criss-cross laces with a tied bow, metal eyelets, a modelled zipper with a slider and a pull tab, a tongue, and a
> rubber sole. There are six PBR faces, and a one-prim LSL HUD recolors them with glTF base-color overrides.
> Everything is generated by headless Blender scripts from the body's dev kit, through the same pipeline as the
> [hobble dress note](rigged-mesh-hobble-dress-for-ebody-reborn-waifus-headless-bl.md). Read that note for the
> rigging, the Collada writer and the skeleton facts; this note covers what was new. The user verified it in
> world on the main grid over ~34 mesh versions and 4 HUD versions.

## Setup
- Viewer: Firestorm 7.2.4.80712 on Windows 11. Main grid: uploads were free on the user's account, so we
  skipped the Aditi beta grid. Free uploads (mesh included) are a Premium Plus benefit; Basic, Plus and Premium
  accounts pay per upload ([secondlife.com/premium](https://epxj.yx-sf.com/zhineng/audience-94345139.html)).
- Blender 4.5 headless: `blender -b <kit.blend> --python build.py`. No Avastar.
- eBody Reborn Dev Kit 2.0, Blender 3.6.7 kit. It has five foot meshes, RebornFeet_1 (flat) to RebornFeet_5
  (ballet/pointe, the toe tip is the lowest point). The boots fit RebornFeet_5 only, so the wearer sets the
  Reborn feet to the highest position. Keep the kit and any `.blend` that contains it out of git and releases
  (kit terms).
- Plain Python 3 (no Blender) writes the glTF material files.

## Route and why
Content route: a rigged `.dae` (both boots in one file, so they upload as one linked object), six
materials-only glTF files, textures, and two LSL scripts (HUD and boots). Second Life is online, so the viewer
and the protocol are not touched.
- Fit against the dev kit only, never against mesh ripped from the viewer. See the dress note's Route section.
- PBR instead of legacy textures (the user asked). This changes the HUD API: legacy `PRIM_COLOR` does not tint
  a PBR face, so the HUD has to use glTF overrides (`PRIM_GLTF_BASE_COLOR`).
- Considered for the HUD: a linkset with one prim per button. Rejected: one prim with one texture, hit-tested
  with `llDetectedTouchST`, is easier for a non-builder to assemble and can't drift out of sync, because a
  single generator writes both the art and the click boxes.

## How the game works (what we had to learn)
- **Face numbers follow the Collada material *name*, sorted alphabetically.** Before upload the viewer sorts a
  model's faces by the `material` symbol of each `<triangles>` block, case-insensitively
  (`LLModel::sortVolumeFacesByMaterialName` in secondlife/viewer), so the order of the blocks in the file
  doesn't matter. Our materials eyelets, laces, overlay, sole, upper and zipper became faces 0 to 5 in that
  order (checked in world with Select Face). Renaming a material therefore renumbers faces and breaks the HUD.
  Prefix names deliberately if you want a particular order.
- **One `.dae` with two meshes uploads as one linked object.** `LINK_SET` in a script in the root reaches both
  boots, and the faces have the same numbers on both, because the right boot is a mirror with the same
  materials.
- **PBR tinting.** A materials-only glTF per face, with near-white base-color, normal and ORM maps
  (R = 1, because AO is baked into the base color; G = roughness; B = metallic). SL multiplies the base-color
  factor by the texture, so a near-white texture plus a tint gives any color, and metallic faces (zipper,
  eyelets) tint like colored metal.
- **`PRIM_GLTF_BASE_COLOR` override** (rule 48): face, texture, repeats, offsets, rotation, color, alpha,
  alpha mode, alpha cutoff, double-sided.
  - The color is **linear** RGB, unlike legacy tint, so convert with `llsRGB2Linear`.
  - An empty string `""` in a slot clears that part of the override, so the material's own value shows. Setting
    only the color is therefore `[PRIM_GLTF_BASE_COLOR, face, "", "", "", "", llsRGB2Linear(c), "", "", "", ""]`.
  - "Reset to the material colors" is the same rule with every slot `""` on `ALL_SIDES`.
- **HUD → worn object messaging.** `llRegionSayTo(avatarKey, nonZeroChannel, msg)` is delivered to every
  attachment of that avatar (wiki: "can be heard by any attachment"). The boots listen on a channel derived from
  the owner key and drop anything where `llGetOwnerKey(id) != llGetOwner()`. That keeps other people's HUDs from
  recoloring your boots. Messages on a non-zero channel don't trigger `llRegionSayTo`'s throttle (the wiki's
  caveats: it counts channel 0, although once tripped it blocks every channel).
- **`llDetectedTouchST` is surface space**, (0,0) bottom-left of the face, and doesn't depend on the
  texture's repeats or offsets or on *which* texture is applied (`llDetectedTouchUV` is texture space). So a
  HUD can swap whole textures to show state, and the click boxes stay valid. The wiki notes that the vertical
  coordinate is flipped on a glTF mesh; a box prim, as here, isn't one.
- **HUD geometry.** HUD attachments have x as depth (a larger x is farther from the viewer), so at
  `ZERO_ROTATION` a box's −X side (face 4) faces the screen and shows its texture upright.
  `llSetLocalRot(ZERO_ROTATION)` in `attach()` turns it to face the viewer. HUD points are 31 to 38
  (`ATTACH_HUD_CENTER_2` to `ATTACH_HUD_BOTTOM_RIGHT`); 39 and up are body points again (neck, avatar centre,
  Bento). One metre of HUD space is the height of the viewer window (wiki: HUD): a 0.22 m panel was unreadable
  and 0.42 m was right on the user's screen.
- **Hover text is a stored prim property.** Removing the `llSetText` call from a script leaves the old text
  floating; clear it explicitly with `llSetText("", ZERO_VECTOR, 0.0)`.
- **SL culls back faces**, unless a glTF material is set double-sided. Open surfaces (a strip, a ring, a tube,
  a stitch quad) show from one side only, so every open part needs its faces oriented deliberately (Gotcha 3).

## Build steps
1. **Shell** (`build_boots.py`, on the kit blend, 17 s):
   - Slice the foot mesh every 2 mm and cut the real skin edges at each height. Take the convex hull, push it
     out 4 mm, and store it as radii along 72 fixed directions round a centre.
   - Smooth (±10 slices, ±3 columns), never closer than 2 mm to the skin.
   - Wedge: union with the foot's footprint up to the heel, then a radius cross-fade into the slices. Add a
     morphological opening for the rounded toe and back corners, and a taper at the base.
   - Mesh rows follow the color edges (sole top, the scooped overlay top, the back panel top), so the faces'
     material boundaries are smooth curves, not stair steps.
2. **Trim on the surface:** a surface parameterisation (fractional column, height) gives point, normal and
   tangents. Eyelet rings, lace tubes, stitch quads, the bow and the zipper are all placed through it, so they sit
   on the curved boot instead of in a plane.
3. **Mirror** the left boot for the right. Rename vertex groups L↔R (Gotcha 2), flip normals, and mirror the
   custom normals. Same topology, so one UV layout serves both boots.
4. **Textures** (`texture_boots.py`, ~70 s):
   - Smart UV project per texture group, then one Cycles bake per map type for all groups (emit → color, AO,
     tangent normal, emit → roughness/metallic).
   - The procedural materials branch on an int face attribute `part` (leather, stitch, zipper teeth, slider,
     tape, tread).
   - The laces are not baked: they carry their own UVs and a tiling braid (Gotcha 4).
5. **Export:** the rigged DAE (the dress note's writer), then one glTF material per face, named
   `<face> WABB <Part>.gltf`.
6. **HUD** (`make_hud.py`): one table defines the parts, the 24 swatches, the metal finishes and every button
   box. From it the script:
   - renders one 1024² texture per selected part with Workbench (flat lighting, Standard view transform, so
     swatches are sRGB-exact; text from a TTF);
   - writes the HUD script and the boots script, with the boxes embedded as `[lo, hi]` vector pairs.

## Verification
- **In world (the oracle):** the user uploaded each version and returned annotated screenshots. Red circles
  marked "behind the laces", yellow marked "looks like a cylinder stuck in", and an orange circle plus a blue dot
  meant "move this to there". Rigging and fit passed on the first test ("no clipping"). The HUD recolored both
  boots on its first test.
- **Automated, in the build:**
  - worst leather-to-skin clearance (3.9 mm) and tongue-to-skin clearance (1.8 mm);
  - zipper face orientation (each face's normal against the nearest shell face: 160/160 outward);
  - the bow's height over the laces, printed per build;
  - the DAE joint list per boot (this caught Gotcha 2).
- **HUD check:** a Blender script parses the *generated* LSL lists. For every swatch and button box it checks
  that the rendered pixel matches the color the script sends (±3/255), and runs a Python port of the hit test.
  It also checks that only the selected part's label is red in each texture and that no boxes overlap.
- **Bake determinism:** re-baking unchanged geometry gave byte-identical maps. So a geometry change confined to
  one material keeps the other materials' UVs valid, although their baked AO can shift.
- **Not verified:**
  - LOD behaviour and land impact (never measured);
  - the other Reborn foot positions (they won't fit);
  - whether the overrides survive taking the boots off and on, and copies;
  - other PBR viewers;
  - the texture-atlas alternative for the HUD (Gotcha 12).

## Gotchas
1. **HUD colored the wrong parts.** **Cause:** the face numbers were assumed from the `<triangles>` order; SL
   orders faces by material name. **Fix:** read the numbers in world (Edit → Select Face) and never rename the
   materials. HUD labels can say anything ("Toe Box" for the material `overlay`).
2. **Mirrored boot followed the left leg.** **Cause:** since Blender 3.0, vertex-group names live on the mesh,
   so `mesh.copy()` brought the L_ groups, and the mirror step wrote weights into them by index. It was invisible
   in rest-pose renders. **Fix:** rename the copied groups with the L↔R map; check the joint list in the exported
   DAE.
3. **Zipper teeth faced into the boot.** **Cause:** the teeth strip was an open surface, and bmesh
   `recalc_face_normals` oriented all 160 faces inward; with back-face culling the teeth were invisible from
   outside. **Fix:** flip each open-part face toward a known outward vector, and use recalc only on closed parts.
   Measure the orientation in the build.
4. **Braided laces showed no braid in world.** **Cause:** an object-space procedural "braid" doesn't follow
   the cords, and 6-sided tubes in a shared atlas had too few texels. **Fix:** 10-sided tubes with their own UV
   layer: u around the cord, v along it in units of the circumference (2πr), so the texels are square. A
   512² tiling braid (two ±45° strand families, over-under, fibre twist) is generated in numpy, not baked.
5. **Bow loops and tails dipped behind the criss-cross.** **Cause:** the bow had a fixed height (3.5–5 mm)
   while the lace arches peak at 4.7 mm. **Fix:**
   - Record the lace centre lines densely (surface point plus height) in a KD-tree.
   - For each bow point, require height ≥ the height of any lace within 2r + 1.5 mm, plus 2r. Widen with a
     windowed max, then a moving average, so it rises smoothly.
   - Tails resting *on* laces then stood ~7 mm off the boot and looked like they floated, so the user asked to
     pull them in. Flatten the two crossings that sit under the bow and let the tails touch the laces
     (clearance 2r).
6. **Knot looked like "a cylinder stuck in" and then like an empty ring.** **Fix:** a cord wrapped twice
   around a sideways axis (oval section, ends tucked against the boot). Each loop's two legs pass *through* the
   wrap, one above the other, so it's solid from every angle. The tails start under the knot, close to the
   leather.
7. **Baked AO darkened whole panels.** **Cause:** the world AO distance defaults to 10 m. **Fix:** 1 cm.
8. **Fine texture detail was lost on the big flat sole.** **Cause:** ~1 mm pebbles over a 25 cm sole in a
   shared 1024 atlas is about 4 px per pebble. **Fix:** a per-group bake size (sole 2048). Voronoi F1 domes ×
   edge-distance grooves at two scales, on noise-warped coordinates, read as rubber pebble grain; a cracked-paving
   look came from edge distance alone.
9. **Blue notch climbing the side of the back panel.** **Cause:** faces between a column whose boundary
   follows the overlay top and one whose boundary follows the panel top stretched diagonally between the two.
   **Fix:** build those columns twice, one per boundary, and merge coincident verts afterwards.
10. **A widened tongue still looked no wider.** **Cause:** only ~6 mm shows above the padded rim, and an 8 mm
    top-corner radius rounded the extra width away. **Fix:** corner radius below the visible height.
11. **Hover text stayed after the script stopped using it.** **Cause:** a stored prim property. **Fix:**
    `llSetText("", ZERO_VECTOR, 0.0)` in `state_entry`.
12. **"Make the selected part's label red" on a static texture.** **Fix:** one texture per state (four
    uploads), swapped with `PRIM_TEXTURE`. It works because touch is resolved in surface space (ST). A 2048 atlas
    with repeats 0.5 and per-state offsets would be one upload, but SL's offset sign convention couldn't be
    checked offline, so we didn't use it.
13. **Windows: Blender seemed to fail with exit 255 after a successful bake.** **Cause:** piping its output
    into PowerShell `Select-Object -First N` closes the pipe early. **Fix:** capture all output, then filter.

## Assets
- No AI-generated assets, and no kit geometry is shipped.
- **Mesh:** all procedural, fitted to the kit feet.
- **Textures:** procedural Blender shader trees baked in Cycles (leather grain, twisted-thread stitches,
  zipper-tape twill, rubber tread), plus numpy for the lace braid.
- **HUD art:** Workbench renders of planes and text objects.
- **Design references:** photos and annotated screenshots from the user, not shipped.

## Cost and time
Two days of sessions. About 34 mesh iterations (shell 19, trim 6, then in-world rounds for the zipper,
laces, opening, tongue, sole and bow) and 4 HUD iterations. Uploads were free on the account (see Setup).

## Open questions
- Which way SL's texture offset shifts the sampled window. This would allow a one-texture state atlas for HUDs.
- Whether glTF overrides persist through copy, transfer and re-wear in all cases (assumed from the wiki,
  not checked).
- Land impact and LOD quality at ~30k triangles per boot with generated LODs.
